# 뉴스 출처 및 라이선스 정책 — 허용 목록(allowlist) 우선 접근

최종 갱신: 2026-10-06

CATCHY는 뉴스 원문을 재게시하는 서비스가 아닙니다. 공개적으로 재사용 조건이
명확한 출처의 **사실관계만 참고**해서, CATCHY가 새로 작성한 영어 학습 콘텐츠
(요약·예문·퀴즈)를 제공합니다. 이 문서는 지금 단계에서 왜 이런 보수적인
구조를 택했는지, 무엇을 의도적으로 제외했는지, 나중에 실제 수집/생성 API를
붙일 때 무엇을 확인해야 하는지를 기록합니다.

## 1. 왜 지금 뉴스 수집 API나 AI 생성 API를 연결하지 않는가

- **법적 리스크 최소화가 최우선입니다.** 외부 API(예: NewsData 같은 뉴스
  애그리게이터)를 붙이면 그 서비스가 실제로 "상업적 재사용·요약·번역·재게시"
  까지 허용하는지 약관을 하나하나 직접 확인해야 하는데, 이번 세션에서는 그
  수준의 검증을 끝내지 못했습니다. 확인되지 않은 권한을 허용된 것처럼
  가정하지 않기 위해, 이번 단계에서는 **외부 뉴스 API 연결을 아예 하지
  않습니다.**
- 같은 이유로 **실제 AI API(예: Claude API) 연결도 하지 않습니다.** 지금은
  `generateTrendDraftFromCandidate`를 규칙 기반(rule-based) mock 생성기로
  구현해서, 무엇을 입력받아 무엇을 출력하는지 함수 경계만 먼저 확정합니다.
  실제 AI 요약/번역을 붙이는 작업은 이 경계를 바꾸지 않고 함수 내부 구현만
  교체하면 되도록 설계했습니다.
- 일반 언론사 기사 본문, 스포츠·연예 매체, AP/Reuters/AFP 같은 통신사 기사는
  처음부터 수집 대상에서 제외합니다. 이들은 대부분 유료 라이선스 계약이
  필요한 것으로 널리 알려져 있고, 이번 범위에서 계약 체결은 다루지 않습니다.

## 2. 왜 "허용 목록(allowlist) 우선" 구조인가

뉴스를 먼저 수집하고 나중에 "이거 써도 되나?"를 검토하는 순서가 아니라,
**재사용 조건이 먼저 명확한 출처만 허용 목록에 올리고, 그 목록 안에서만
콘텐츠 후보를 고르는** 순서로 설계했습니다.

- `getAllowedSources()`가 반환하는 출처 목록은 코드에 하드코딩된 정적
  데이터입니다. 크롤러가 알아서 새 출처를 찾아 추가하지 않습니다.
- 오늘 다룰 콘텐츠 후보(`getDailyContentCandidates()`)도 외부 API 호출 없이
  서버 코드에 내장된 시드(seed) 데이터입니다. 하루 3건 이하로 가정합니다.
- `validateContentCandidate()`가 허용 목록 조건을 통과하지 못한 후보는 초안
  생성 단계로 넘어가지 못하게 걸러냅니다.

이 구조 덕분에 "권한이 불명확한 출처를 썼는지"를 사람이 매번 수동으로
검토할 필요 없이, 코드 자체가 조건을 강제합니다.

| Global Voices | CC BY 3.0 | 허용 | 허용 | 시민 저널리즘 매체. 자체 저작 기사(제3자 사진/영상 제외)에 대해 상업적 재사용과 번역·각색을 명시적으로 허용. 저작자 표시 필요. |

## 4. 처음부터 제외하는 콘텐츠 유형

- 일반 언론사(스포츠·연예 매체 포함)의 기사 **본문** — 재사용 조건이 출처마다
  다르고 대부분 확인되지 않았으므로 기본 제외.
- AP, Reuters, AFP 등 통신사 기사 — 통상 유료 라이선스 계약이 필요.
- SNS 게시물·댓글·스크린샷 — 플랫폼 약관과 작성자 개인의 권리가 함께
  얽혀 있어 재사용 판단이 복잡함.
- 사진, 썸네일, 영상, 가사, 대사, 밈 이미지 — 텍스트와 별도의 저작권 체계를
  가지므로 CATCHY는 이미지/영상을 아예 사용하지 않음.
- "재사용 가능 여부 확인 필요"로 분류되는 출처 — 확인 전까지는 허용된 것으로
  간주하지 않고 기본적으로 제외.
- 원문 전체를 읽거나 저장해야만 이해할 수 있는 콘텐츠 — CATCHY는 원문 전문을
  수집·저장하지 않고, 사람이 직접 요약한 짧은 사실 메모(`factMemo`)만 다룸.

## 5. 저작자 표시(attribution) 원칙

- `Trend.sources[]`에는 출처명, 원문 제목, 원문 링크, 발행일, 라이선스명,
  라이선스 링크, 이용 조건 메모를 모두 남깁니다.
- 원문 제목(`originalTitle`)은 출처 영역 표시용으로만 쓰고, 홈 화면과 학습
  화면에서는 CATCHY가 새로 지은 제목을 우선 노출합니다.
- 원문 링크는 항상 새 탭(`target="_blank"`)과 `rel="noopener noreferrer"`로
  열리며, 링크 미리보기·OG 이미지·썸네일은 렌더링하지 않습니다.
- 트렌드 상세 페이지 출처 영역에는 다음 문구를 그대로 표시합니다: "이
  콘텐츠는 공개 출처를 참고해 CATCHY가 영어 학습용으로 재구성한 요약입니다.
  원문 전문은 각 출처 링크에서 확인해 주세요."

## 6. 이미지·영상·원문 전문을 쓰지 않는 이유

- 사진·영상은 기사 텍스트와 별개의 저작권/초상권 문제를 가지며, 출처가
  텍스트 재사용을 허용하더라도 이미지까지 허용한다는 뜻은 아닙니다.
- 원문 문장을 그대로 베끼면(요약이 아니라 복제) 라이선스가 요구하는 "번역·
  요약·각색"의 범위를 벗어날 위험이 있습니다. 그래서 CATCHY 콘텐츠 생성은
  원문 문장이 아니라 사람이 직접 적은 짧은 사실 메모(`factMemo`)만 참고
  재료로 사용합니다.
- 긴 원문 스타일 요약도 "요약"이 아니라 사실상 "재게시"에 가까워질 수
  있으므로, `validateContentCandidate`에서 `factMemo`가 기사 본문 수준으로
  길어지지 않았는지 확인합니다.

## 7. 나중에 실제 뉴스 API / AI API를 붙일 때 확인할 체크리스트

1. 후보 API(예: 뉴스 애그리게이터, 특정 매체 API)의 **공식 이용약관 전문을
   직접 열람**해서 상업적 이용·요약·번역·재게시가 명시적으로 허용되는지
   확인한다. 블로그 요약이나 검색엔진 발췌만으로 판단하지 않는다.
2. "출처 표시만 하면 된다"는 식의 막연한 가정을 하지 않는다. 표시 의무와
   재사용 허용 범위는 별개 조항일 수 있다.
3. 이미지·영상·SNS 삽입물 등 텍스트 외 콘텐츠는 별도 약관이 적용될 수
   있으므로 텍스트 재사용 허용과 분리해서 검토한다.
4. 확인 결과를 이 문서의 3번 표와 같은 형식으로 기록하고, "직접 확인"과
   "간접 확인(검색엔진 인용 등)"을 명확히 구분해서 남긴다.
5. `getAllowedSources()`에 새 `AllowedSource` 항목을 추가할 때는
   `allowed`, `allowsCommercialUse`, `allowsAdaptation`을 실제 확인된
   내용과 다르게 낙관적으로 설정하지 않는다.
6. 실제 AI API를 `generateTrendDraftFromCandidate` 내부에 연결할 때도,
   입력으로 원문 전문을 통째로 넘기지 않는다 — 여전히 `factMemo`처럼 짧고
   사람이 가공한 사실 메모만 입력으로 사용해, 모델이 원문을 그대로 베껴
   쓰는 결과물을 만들지 않도록 한다.
7. 자동 수집을 붙이게 되더라도 해당 사이트의 `robots.txt`, 요청 빈도 제한,
   접근 제한(로그인/유료벽)을 그대로 지킨다. 우회 기법은 사용하지 않는다.
8. API 키 등 비밀값은 서버 전용 모듈에서만 다루고, `NEXT_PUBLIC_*` 접두사가
   붙은 환경 변수에는 절대 넣지 않는다. `.env.local`은 git에 커밋하지 않는다
   (저장소의 `.gitignore`가 이미 `.env*`를 제외하고 있음).
